## 0. 一句话现状

**`observe()` 是 pull，所以采集速率被消费者绑住。** 调用方问一次给一张，节奏是"拍 → 处理 → 拍 → 处理"；把慢 observer 甩到别的线程也不解决——快 observer 的耗时、加上调用方拿到帧之后自己做的事，仍然堵在下一次 `observe()` 前面。

而相机天然是 **push**：它按自己的帧率吐。

本轮给 `Sensor` 加**连续流**模式：一条采集线程按自己的节奏采，观测进**每消费者一条的有界队列**，跟不上的消费者**丢帧而不是拖慢相机**。`observe()` 一行不改，作为"按需一张"保留。**pluck 侧代码完全不动**，记录/存储层不在本轮。

## 1. 起因：pull 模式的结构缺陷，有实测

这不是纸上推演。pluck 已经完整地撞上过一次，而且把每个数都量了下来。

### 1.1 消费是生产的 8 倍

相机 B 一帧 4024×3036×3 = **35 MB 裸帧**。把它 PNG 压掉，工控机上 **~247 ms**
（`backend/src/workers/sample_writer.py:4-8`；开发机 `cv2.imwrite` 0.26–0.31 s，
`cv2.imencode` 单独 0.29 s —— **基本全是压缩的 CPU 开销，不是磁盘 IO**）。

而采一帧 `capture()` **≈31 ms**（区间 8–67 ms，推导见
`backend/src/workers/drill_vision.py:88-95`）。

**247 ÷ 31 ≈ 8。** 存盘这一个消费者，比相机本身慢 8 倍。

### 1.2 后果：钻头抬升那几秒只采到 1–3 帧

原来这 247 ms 花在**采帧线程里**，所以连拍的服务时间就是 **288 ms/帧**；
而平移窗口只有 **0.05–0.30 s**。于是每次抬升只采到 **1–3 帧**
（`drill_vision.py:79-83`）。

pluck 自己的结论值得整句引用：

> **调 `lift_move_step_mm` 毫无用处**：0.5 mm 的门在 70–100 mm/s 下每 5–7 ms 就满足一次，
> **卡的是服务时间不是触发门槛**。

**这句话就是 pull 模式缺陷的完整诊断。** 触发条件再密也没用——因为下一次采集要等上一次消费做完。

### 1.3 pluck 的解法，正是本文要一般化的东西

`ffcb725`（"存图移出采帧线程 —— 服务时间 288ms -> 41ms"）把压缩挪到一条写盘线程上，
服务时间 **288 ms → 41 ms，7.1×**。每次平移能采到的帧数
（窗口 ÷ 服务时间，`drill_vision.py:96-98`）：

| 平移窗口 | 改造前 | 改造后 |
|---|---|---|
| 0.05 s | 1 | 2 |
| 0.10 s | 1 | 3 |
| 0.30 s | 2 | 8 |

**新瓶颈不再是消费者**：31 ms/帧 ≈ 24 fps 的相机够快了，卡的是平移窗口本身只有 0.05–0.30 s。

一个关键的实现事实，它决定了本文 §3.1 的否决：
**`cv2.imwrite` 释放 GIL** —— 实测一条 Python 忙等线程在 `imwrite` 期间仍跑到
**97% 的空载速率**（`sample_writer.py:13-14`）。**所以把压缩挪到另一条线程是真并行，不是假的。**

### 1.4 所以采集线程不是新增，是搬家

pluck 为此长出了 `drill-lift-stream` 线程 + 异步写盘。它今天跑在**业务 Worker 里**。

**本轮做的事是把这条线程下移到 `Sensor`，不是凭空造一条。** 框架只给了 pull，
push 只能业务自己造——造完还得手写两套东西互相避让（§2.3 末）。

## 2. 已达成的结论

### 2.1 两种模式，**显式切换**，不是同时

| 模式 | 谁用 | 形状 |
|---|---|---|
| **按需一张**（pull） | 扫描位停稳拍照 | 就是今天的 `observe()`，**一行不改** |
| **连续流**（push） | 抬升连拍、预览 | `Sensor` 自己的采集线程按自己节奏采 |

**BT 说开始/停止流。** 理由是成本：连续采集一直烧总线和带宽，而相机 A 只在扫描位需要、
相机 B 只在抬升时需要。让它们默认长流是白烧。

> **为什么不是"两种模式同时开"**：同一台设备被两个节奏同时驱动，就退回到 pluck 今天手写
> "连拍线程活着时 `on_tick` 让路"（`drill_vision.py:590`）的局面——那正是要消掉的东西。
> 一台设备同一时刻只有一个驱动者。

### 2.2 采集线程的硬判据 —— **这是不破坏地基的关键**

> **采集线程不写 control state、不发 note、不参与判据。它只把观测放进队列。**

**BT 仍然是唯一的「控制」调度方。**

`architecture.md:51` 的原文是：

> **单一节拍源**：任何 **Worker** 不得维持自己的心跳。慢操作走 `run_async`；长时后台 worker 走 `run_background`。

**这条约的是 Worker**——参与控制的那一层：接 note、写 state、BT 从它读判据。
**`Sensor` 不是 Worker。** EVO-011 当时把这条禁令推广到了设备层，那是过度推广
（详见 EVO-011「修订 2」）。承重的判据更窄，而且完好无损——就是上面那一句。

用户的框定，写在这里作为判断依据：

> **BT 更多的是统一调度和保证时钟同步，大脑其实不完全关心手臂和四肢。**

**时钟同步因此是 `Sensor` 的硬责任**：采集线程各跑各的，但 `captured_at` 必须来自
**同一个时钟**，否则多相机观测之间、以及观测与臂轨迹之间都对不齐。

### 2.3 **每消费者一条有界队列**，不是一个共享环

理由是**业务的**，不是技术洁癖。pluck 的实证（`sample_writer.py:16-26`）：

- **留档必须丢最新。** 每次抬升的 `0001` 是**参考帧**——判定"钻头上有没有毛"是拿后面的帧
  跟它比。丢最旧就会丢掉它，**丢了整个 poke 的数据就废了**；而且离线读法
  （`sorted(dir)` → `frames[0]` 是参考）依赖它在盘上。
- **预览要的恰恰是最新那张**，旧的扔掉毫无损失。

**同一路观测，两个消费者的正确策略完全相反。一个共享环只能有一种策略，所以必须是每消费者一条。**

代价很低，因为**帧只存一份**：队列里放的是**引用**，不是拷贝
（pluck 原话：「不拷贝帧: 队列里存的就是调用方传进来的那个 ndarray 引用」，
`sample_writer.py:64-65`）。内存 = 活着的帧数 × 帧大小，一帧活到最后一个持有者放手。

> **顺带消掉的两处手写仲裁**：`ThreadSafeCamera`（`backend/src/camera.py:57`，把 `capture()`
> 串行化，好让后台录像线程、连拍线程和主 note handler 共用一路相机流）和
> `drill_vision.py:590` 那句"连拍线程活着 → 它在喂画面，这里让路"。
> **一台设备一个驱动者之后，这两段都是不需要写的代码。**

### 2.4 引用永不失效；有界性靠**入队时拒绝**实现

`submit()` 要么**接受**（那一帧活到用完），要么**当场返回 `False`**
（`sample_writer.py:87`：「入队一帧。**从不阻塞, 从不抛。** 返回 False = 队列满, 这帧被丢了」）。

**不做"事后过期 / 环绕失效"的设计。**

这一下消掉三个麻烦：

- 没有环绕 → 没有脏读
- 没有"消费者能持有多久"的生命周期难题
- **"你没拿到"从异步的、事后的，变成同步的、当场的** —— 调用方立刻知道，可以立刻记账

> ### ⚠️ 这一条更正 EVO-011 §5.6
>
> EVO-011 §5.6 立的契约是：「观察者持有一份观测的引用之后，要么拿得到数据，要么明确拿不到
> ——**引用失效必须是显式结局**」。那条**预设了"会有失效"这回事**，因为它假想的实现是
> 「有界环 + 引用过期」。
>
> **本文认为那个方向是错的。** 正确的形状是**入队即拥有**：拒绝发生在**入队那一刻**，
> 一旦收下就永不失效。§5.6 想防的脏读因此根本不会发生——不是"处理得好"，是**不存在**。
>
> §5.6 的**动机**仍然成立（"记录器是最慢的那个观察者，别让它拿到的数据在手里烂掉"），
> 只是解法换了。EVO-011 §5.6 处已加指向本节的更正提示。

### 2.5 三样东西都由**业务/配置**决定，不是框架常量

| 决定什么 | 由谁定 | 为什么不能是常量 |
|---|---|---|
| **队列深度** | 按 sensor 配 | A 是 2048×1536 → **9.4 MB/帧**；B 是 4024×3036 → **35 MB/帧**。**差 4 倍**，一个全局默认对谁都不合适 |
| **丢帧策略** | 按 consumer 配 | §2.3：留档要 `drop_newest`，预览要 `latest_only`。**同一路观测，策略相反** |
| **采集模式** | 由 BT 编排 | §2.1：什么时候该连拍、什么时候停稳拍一张，是业务流程 |

至少要提供两种丢帧策略：**`latest_only`**（深度 1，永远覆盖成最新——给预览）和
**`drop_newest`**（有界，保住最早的——给留档）。框架不预设哪个是默认。

> A 的分辨率不是从 config 猜的：`config/pluck.yaml` 里 `width/height` 那两行标着 `mock-only`。
> **2048×1536 来自实测样本**——`drill_vision.py:90-91` 记着 A 的写盘耗时统计是
> 「191 个样本, 2048×1536 / 4.5MB」（4.5 MB 是盘上的 PNG，9.4 MB 是内存里的裸帧）。

### 2.6 丢帧**必须记账**，而且账由 BT **主动来取**，不是回调推

**记账是硬要求。** pluck 原话（`sample_writer.py:23-25`）：

> **丢了必须记进 events.jsonl** —— **静默丢帧离线才发现, 那是最坏的情形。**

理由在 `drill_vision.py:531-534` 写得更透：离线看到帧数比预期少时，这一行说明少的是
**"队列满丢的"**而不是**"相机没采到"**——**两者的处置完全不同**。

**但账的流向是"取"不是"推"**：

- 写盘线程满了丢帧，**只加计数器，不通知任何人**
- BT 在它**本来就要停下来**的时刻（一次 poke 结束、`on_stop`）调一次 `take_dropped()`
  **取走并清零**，写一行日志

`sample_writer.py:107-116` 的 docstring 把理由写死了：

> 调用方负责把它记进 events.jsonl —— 结账刻意留在**调用方的线程**上（BT 时钟线程），
> 与 episode ledger "所有 runlog 写入单线程" 的约定一致。

调用点：`drill_vision.py:506`（`_stop_stream`）与 `:261`（`on_stop`，排空超时放弃的帧走同一条账）。

**每帧推一次回调 → 变成每次 poke 主动取一次账。** BT 只在它本来就要付的那个时刻付这点代价。

### 2.7 回调是**例外**，不是默认

用户的要求很直接：**BT 不该关心这些。** 落成契约就是三条：

| 消费者类型 | 要不要回调 | 说明 |
|---|---|---|
| **纯副作用**（写盘、编码、发网络） | **不要** | 干完就完了，没有结果要给谁。**BT 全程不知情，也不该知情** |
| **产出 BT 判据**（检测） | 要回到 tick 线程 | 但这**不是"回调通知 BT"**，而是**写 WorldBoard 这个动作必须在 tick 线程上做才安全**。BT 该读的时候自己去 board 上读，没人主动通知它 |
| **统计信息**（丢帧数） | **不要** | 走 §2.6 的"BT 主动来取" |

**流向图 —— 注意中间没有环：**

```
数据往下流：  Sensor ──> Observer ──> 队列 ──> 干活的线程
                                                  │
账往上取：    BT ──── take_dropped() ─────────────┘
              (在它方便的时候, 比如一次 poke 结束)
```

**`Sensor` 从头到尾不需要知道下游发生了什么。** 没有"回到 BT、再由 BT 通知 sensor"这回事。

### 2.8 **不保证 no-drop** —— 写成明确契约

没有 no-drop 保证。**只有"够深 + 满了必须记账"。**

为什么不能有：**真要保证一帧不丢，唯一的办法是让消费者反压生产者**——而那正好是本文要拆掉的东西。

pluck 的处理很诚实，算式全在 `sample_writer.py:48-62`：

- 队列 **12 帧** × 35 MB = **~420 MB 上限**（`DEFAULT_CAPACITY = 12`）
- 采帧 41 ms/帧、写盘 247 ms/帧、一条写盘线程 ⟹ 连续平移时积压以 **20 帧/秒** 增长
- 12 格能吸收 **~0.6 s 的连续平移**
- 现场平移窗口是 0.05–0.30 s ⟹ **生产上一帧都不会丢**

**并且它自己写下了下一步会撞墙的地方，要一并继承：**

> ⚠️ **平移窗口若被放慢到 0.6 s 以上，这里就会开始丢帧** —— 而"放慢平移"正是想多采帧的下一步。
> 那时的解法是**多开写盘线程**（**6 条**才追得上采帧），**不是把队列加深**：35 MB/帧，
> 3 s 平移要 62 帧 = **2.6 GB** 缓冲，**加深只是把丢帧换成吃内存**。

> **多线程写盘有个前置条件**（`sample_writer.py:31-36`）：现在**一条**写盘线程 + FIFO 保证
> 落盘顺序 == 采集顺序，"0001 就是参考帧、字典序即时序"靠的就是这个。要多开线程，得先把
> **落盘序号改成入队时分配**（现在在写的时候分配，多线程会把号打乱）。**本轮不做，但要写下来。**

## 3. 考虑过但否决的

### 3.1 引入 asyncio / event loop —— **否决**

讨论中提过"做成 event loop 这种形式不就解耦了"。**解耦的诉求是对的，而且已经满足了**
（`Sensor` 发布 / `Observer` 订阅就是这个形状）。但**引入一个 asyncio 事件循环**要否掉，四条理由：

**一、会变成第三套并发模型。** AutoWeaver 现在是 BT tick 线程 + `ThreadPoolExecutor`
（`src/autoweaver/worker/async_pool.py:14`）+ daemon 线程，**全是线程**；
全仓 `asyncio` **零命中**（实测 `grep -rn asyncio src/ --include=*.py | wc -l` → `0`）。
再塞一个事件循环进去，就是两套并发模型在同一个进程里共存——死锁最爱长的地方。

**二、瓶颈根本不是 asyncio 擅长的那种。** asyncio 的本事是"等 IO 的时候让出控制权"，而我们卡在：

- **PNG 压缩 247 ms 是 CPU 密集**（§1.1 已确认："基本全是压缩的 CPU 开销，不是磁盘 IO"）
- **大恒相机 SDK 是阻塞的 C 调用**，`await` 不了

两者都得丢进线程池 —— **绕一圈又回到线程**。

**三、有个便宜 asyncio 拿不到。** §1.3 的实测：`cv2.imwrite` **释放 GIL**，
所以写盘线程和采帧线程是**真并行**（采帧线程仍跑 97% 空载速率）。
asyncio 的单线程事件循环拿不到这个。

**四、event loop 最值钱的那个性质，框架已经有了。** 事件循环真正好用的地方是
"所有回调都在一个已知的地方、按确定的顺序执行"。`run_async` 已经是这样
（`src/autoweaver/worker/base.py:236-247`）：

> ``fn`` runs in a worker thread. When it finishes, exactly one completion callback is
> invoked on the **main tick thread** at the start of the next tick... Running on the tick
> thread guarantees that anything the callback does (writing state, reading state,
> mutating self) is free of concurrency concerns.

而且它是**围绕 BT 时钟建的**，比通用事件循环更贴合。

> **注意仓库里已有的 `EventBus` 帮不上忙**：`src/autoweaver/reactive/event_bus.py:36-44`
> 的 `publish()` 是**同步**的——在调用方线程上把 handler 挨个调一遍。
> **那正好是本文要摆脱的"拍 → 处理 → 拍"。** 它目前只有 `state_machine` 在用。

**结论：要 event loop 的语义（解耦 + 回调收敛到一个已知点），不要 asyncio 的运行时。**

### 3.2 一个共享环，所有消费者共用 —— 否决

见 §2.3：丢帧策略因消费者而异，且**方向相反**（留档丢最新、预览要最新）。
一个环只能有一种策略。而每消费者一条队列的额外成本只是引用，不是像素。

### 3.3 「有界环 + 引用过期」（EVO-011 §5.6 的原方案）—— 否决

见 §2.4。换成"入队即拥有 + 入队时拒绝"，脏读不是被处理掉，是**不存在**。

## 4. 本轮范围 / 不做 / 待定

### 4.1 做

- `Sensor` 的**连续流**模式：一条采集线程 + 显式的开始/停止
- **每消费者一条有界队列**，深度按 sensor 配、策略按 consumer 配
- **入队时拒绝**语义（`submit()` 当场返回成功/失败）
- **丢帧计数 + 由调用方主动取走**的记账接口
- `observe()`（pull / 按需一张）**一行不改**，与连续流并存

### 4.2 不做

- **pluck 侧代码完全不动。** 等感知层整体做完一起升——届时一次性处理：
  import 路径、`capture()` → `observe()`、以及 §5 那个 `FreshFrameDahengCamera` 陷阱。
- **记录 / 存储层不在本轮**（telemetry、runlog、PLC 运行数据落盘）。那是下一轮讨论。
  本文只管"观测怎么从相机流到消费者手里"，不管"消费者把它存成什么"。
- **多写盘线程 / 落盘序号入队时分配**（§2.8 末的前置条件）。
- **pipeline 迁移**（EVO-011 §2.7，结论有效、排期推后）。

### 4.3 向后兼容 —— 硬约束

**`observe()` / `capture()` / `snapshot()` 一个都不许删。**

理由见 EVO-011 §5.0 与 §1.6：pluck 生产路径**全部走 `capture()`**，
而那个方法在 `sensor/camera/base.py` 里标的是 "Backward compat alias… new code should call
`snapshot()`"。**框架叫人别用的那个别名，正是唯一承重的入口。**
清账顺序是死的：**pluck 先迁到 `observe()`，才能清那笔 alias 化石账。**

## 5. 顺带可能退役的东西（**预期，需真机确认，不要写成已解决**）

`Sensor` 连续采集且**总在排空**时，队列里不会积压陈旧帧 ⟹ 理论上
`FreshFrameDahengCamera` + 它的 `flush_queue()` 可以退役。

**连带一个陷阱也会消失**：EVO-011 §5.3 记的那个——
`backend/src/fresh_frame_daheng.py:22` 覆盖的是 **`capture()`**，而 `observe()` 走
**`snapshot()`**，两条路不交叉，所以 pluck 一旦改用 `observe()`，
`flush_queue()` 会被**静默绕过**（不报错，只是图可能是旧的）。

> ⚠️ **但 `trigger_mode` 那条路至今没在真机上走过**（EVO-011 §5.3：pluck 从未设置过它，
> 一直用默认的 `False` + `flush_queue()`）。**所以以上全部是预期，不是结论。**
> 真机上要实测确认的是：软触发下的实际帧延迟、以及连续流模式下"总在排空"这个前提是否真的成立。

## 6. 本文最站不住脚的一条

**§2.1「两种模式显式切换，不是同时」。**

它现在靠的是"业务上 A 只在扫描位需要、B 只在抬升时需要，所以不会同时"。**但这个前提未必守得住**，
而且 pluck 自己已经有一个反例苗头：**相机 A 在空闲时跑 16 fps 的直播预览**
（`config/pluck.yaml:451` 的 `live_preview_every_ticks: 3`），**同时**又要在扫描位
"停稳拍一张"。今天这两件事都走 pull 所以不冲突；连续流一上，
**"预览要长流"和"扫描要按需一张"就落在同一台设备上了。**

切换的时序也没定：BT 说"停流"到采集线程真的停下来之间有个窗口，这期间来一次 `observe()`
会发生什么？现在没有答案。

**可能的出路**（本文不选，留给实现时撞上再定）：让 pull 在流模式下退化成"取队列里最新那张 +
告诉你它多老"，由调用方根据 `captured_at` 判断够不够新——臂停稳时，1/16 s 的年龄完全无害。
**那样两种模式就不必互斥了。** 但这会改变 pull 的语义（不再保证"此刻现拍"），
需要先确认没有哪个消费者依赖"这张图是我要的那一刻拍的"。

**这一条是本轮最可能返工的地方。**
